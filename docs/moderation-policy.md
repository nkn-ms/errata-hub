# 投稿モデレーション方針（運用内規）

通報・削除要請が来たときに運営者（管理者）がどう判断・対応するかの内規。
法的根拠は利用規約 **第9条（禁止事項）・第10条（投稿の削除・モデレーション）**（`docs/legal/terms-draft.md` ＝ `/terms` として公開済み）。本書はそれを実際の判断基準・手順に落としたもの。

策定: 2026-07-12（方針3点はユーザー確定済み: 事実誤認は併記対応 / 一次返信7日目安 / 削除時は投稿者へ通知）

## 基本姿勢

- **即時公開＋事後対応**（事前審査はしない。design.md §3 の公開ポリシーと同じ）。
- 原則は「**疑わしきは残す**」。ただし人格攻撃・個人情報・なりすましは即削除の例外。
- 正誤の争いを運営者が裁かない。**争いは削除ではなく透明性（両論併記）で解決する**。

## 部分マスキング（2026-07-22 追加・実装は未了）

「有用な指摘に、問題箇所が一部だけ混ざっている投稿」を**丸ごと削除せずに救う**ための措置。上の表の 1（誹謗中傷）・2（過剰転載）・5（個人情報）で、**問題が投稿の一部に限られ、残りに価値がある**ときに使う。

規約上の根拠は **第6条3項**（表示上の整形と、権利侵害部分の削除・マスキングに限った編集許諾＋その範囲での著作者人格権不行使）。範囲を絞る代わりに、運営者側に次の2つを課している:

1. **編集したことを投稿の表示上に明示する**（規約上の義務）— 黙って書き換えない。規約は読まれない前提に立つと、誠実さは「同意を取った」ではなく「**やったことが見える**」でしか担保できない
2. **投稿者へ通知する**（努力義務）— 削除時の通知（対応フロー5）と同じ扱い。当面は手動送信

⚠️ **本文についてはこの措置を実行できない**（管理画面に投稿本文の編集機能が無く、`ReportUpdateSchema` も status / statusNote / fixedEdition / fixedPrinting しか受けない）。したがって本文は当面「削除」か「そのまま」の二択で運用する。
⚠️ 本文のマスキングを実装する際は、上の 1（表示上の明示）を**同じ PR で必ずセットにする**こと。マスキングだけ先に作ると規約違反の運用になる。

✅ **添付画像だけは1枚単位で削除できる**（2026-07-29 実装。管理画面の投稿詳細「この画像を削除」）。問題が画像に限られるなら、投稿を丸ごと消さずに済む。🔲 **運営者が画像を削除したことは公開ページに出す**（2026-08-11 ユーザー決定・**実装は未了**）。以前は「本文に手を加えないので明示は要らない」と整理していたが、**画像も投稿コンテンツであり、黙って消せば読み手には最初から無かったのと区別が付かない**。上の 1 と同じ理由で出す。⚠️ **投稿者自身による削除は明示しない**（自分の投稿の修正であって、他人の著作物への改変ではない＝規約第7条と第6条3項の違い）。

## 出版社からの回答（2026-08-12 追加）

規約 **第8条**により、運営者が権限を付与した出版社等の担当者が、自社に関係する投稿へ**公開ページから直接回答できる**。届いた回答を運営者が代わりに記載することもでき、その場合は「運営者が代理で記載」と画面に明示される（第8条4項）。

モデレーション上、押さえておくこと:

- **回答は書いた本人も取り消せない**（第8条3項）。投稿者の追記と同じ扱いで、出版社が確認した時点の内容が後から書き換わらないようにするため
- ⇒ **不適切な回答を消せるのは運営者だけ**。管理画面の投稿詳細「出版社からの回答」に削除ボタンがある（規約 第10条1項に基づく措置・操作は AuditLog に残る）。**投稿ごと消さずに回答1件だけ消せる**のは、添付画像を1枚だけ消せるようにしたのと同じ考え方
- **なりすましは付与の段階で防ぐ**。回答の権限は管理画面のユーザー編集から個別に付与するもので、技術的な検証は無い（担保は付与前の運営者の確認だけ）。⚠️ 権限を持つ人は**公開ページに文章を書ける**ので、「表示に使うだけ」だった頃の感覚で付けないこと
- 出版社が回答してもステータスは自動では動かない。「修正予定」等への更新は運営者が内容を確認して行う

### 削除が先・差し替えは後（2026-08-11 変更）

以前は「投稿者へ差し替えを依頼→対応がなければ削除」の順だったが、**削除を先に置く**。

1. 依頼から返信までの間、**権利侵害の状態が公開されたまま**になる。規約第10条1項は事前通知なしの削除を認めており、投稿者の許可を待つ必要はない
2. **投稿者は連絡後の投稿にも追記フォームから画像を足せる**（PR#190。追記の画像枠は本体とは別で5枚）。だから「消してから、範囲を絞った画像を足し直してもらう」が成立する。この手段が無かった頃は「先に依頼」が合理的だった
3. 代償は、その画像が指摘の根拠だった場合に**一時的に指摘が成立しなくなる**こと。対応フロー5の通知で「追記から足し直せる」ことを必ず案内して埋める

## 対応フロー

1. **受付** — 窓口はメール `nkn-ms+errata-hub@hotmail.co.jp`（規約第10条2項に記載。通報ボタン=Flag は未実装・将来課題）
2. **一次返信** — 受領した旨を**7日以内**を目安に返信（内規の目標値であり規約上の義務にはしない。規約上は「合理的な範囲で対応」）
3. **判断** — 上の表に当てはめる。迷ったら「疑わしきは残す」に倒す
4. **対応** — 削除は管理画面の削除機能で行う（物理削除＋AuditLog に before データが自動記録される）。**問題が添付画像だけなら投稿詳細の「この画像を削除」で1枚だけ消す**（投稿本文は残す）。併記対応はステータス変更＋出版社からの回答（公開ページの投稿詳細から記載する）
5. **通知** — 申立て者へ結果を返信する。**削除した場合は投稿者にも通知する**（当面は Profile のメールアドレス宛に手動送信・将来は削除 API からの自動送信に移行）。**画像だけを削除した場合は、範囲を絞った画像を追記フォームから足し直せることを案内する**
6. **記録** — AuditLog が自動で残る（90日で自動削除・プライバシーポリシー整合）。判断に迷った事例はこのファイルに追記して基準を育てる
