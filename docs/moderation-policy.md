# 投稿モデレーション方針（運用内規）

通報・削除要請が来たときに運営者（管理者）がどう判断・対応するかの内規。
法的根拠は利用規約 **第7条（禁止事項）・第8条（投稿の削除・モデレーション）**（`docs/legal/terms-draft.md` ＝ `/terms` として公開済み）。本書はそれを実際の判断基準・手順に落としたもの。

策定: 2026-07-12（方針3点はユーザー確定済み: 事実誤認は併記対応 / 一次返信7日目安 / 削除時は投稿者へ通知）

## 基本姿勢

- **即時公開＋事後対応**（事前審査はしない。design.md §3 の公開ポリシーと同じ）。
- 原則は「**疑わしきは残す**」。ただし人格攻撃・個人情報・なりすましは即削除の例外。
- 正誤の争いを運営者が裁かない。**争いは削除ではなく透明性（両論併記）で解決する**。

## 部分マスキング（2026-07-22 追加・実装は未了）

「有用な指摘に、問題箇所が一部だけ混ざっている投稿」を**丸ごと削除せずに救う**ための措置。上の表の 1（誹謗中傷）・2（過剰転載）・5（個人情報）で、**問題が投稿の一部に限られ、残りに価値がある**ときに使う。

規約上の根拠は **第6条3項**（表示上の整形と、権利侵害部分の削除・マスキングに限った編集許諾＋その範囲での著作者人格権不行使）。範囲を絞る代わりに、運営者側に次の2つを課している:

1. **編集したことを投稿の表示上に明示する**（規約上の義務）— 黙って書き換えない。規約は読まれない前提に立つと、誠実さは「同意を取った」ではなく「**やったことが見える**」でしか担保できない
2. **投稿者へ通知する**（努力義務）— 削除時の通知（対応フロー5）と同じ扱い。当面は手動送信

⚠️ **現状この措置は実行できない**（管理画面に投稿本文の編集機能が無く、`ReportUpdateSchema` も status / publisherComment / fixedEdition / fixedPrinting しか受けない）。したがって当面は「削除」か「そのまま」の二択で運用する。実装する際は、上の 1（表示上の明示）を**同じ PR で必ずセットにする**こと。マスキングだけ先に作ると規約違反の運用になる。

## 対応フロー

1. **受付** — 窓口はメール `nkn-ms+errata-hub@hotmail.co.jp`（規約第8条2項に記載。通報ボタン=Flag は未実装・将来課題）
2. **一次返信** — 受領した旨を**7日以内**を目安に返信（内規の目標値であり規約上の義務にはしない。規約上は「合理的な範囲で対応」）
3. **判断** — 上の表に当てはめる。迷ったら「疑わしきは残す」に倒す
4. **対応** — 削除は管理画面の削除機能で行う（物理削除＋AuditLog に before データが自動記録される）。併記対応はステータス変更＋出版社コメント
5. **通知** — 申立て者へ結果を返信する。**削除した場合は投稿者にも通知する**（当面は Profile のメールアドレス宛に手動送信・将来は削除 API からの自動送信に移行）
6. **記録** — AuditLog が自動で残る（90日で自動削除・プライバシーポリシー整合）。判断に迷った事例はこのファイルに追記して基準を育てる

**現状で足りているもの:** 管理画面の削除（物理削除＋AuditLog）・ステータス「修正なし/却下」・出版社コメント・メール窓口。

**将来課題（トラフィック増加時。design.md §4 参照）:**
- Flag（通報ボタン）＋管理キュー

- 非公開化ステータス（削除より軽い一時措置）
- レート制限・新規ユーザーの trust level
