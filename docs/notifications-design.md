# 通知基盤の設計（提案・未確定）

**ステータス: 提案段階（2026-07-15 起草）。実装前にユーザーの方針承認が必要。**
承認後に実装し、確定した運用は docs/design.md §7 へ反映する。

## 0. 用語

- **トランザクションメール**: ユーザーの操作やシステムのイベントに紐づいて1通ずつ送る業務メール（例: 「あなたの投稿のステータスが変わりました」）。不特定多数に一斉送信する広告メール（マーケティングメール）とは配信基盤・法的扱いが別物。
- **Resend**: トランザクションメール送信の SaaS。HTTP API と SDK でメールを送る。
- **SPF / DKIM**: 送信ドメインのなりすましを防ぐ DNS ベースの送信元認証。独自ドメインから送るには DNS にレコードを追加して検証を通す必要がある。

## 1. 何を解決するか（現状の空白）

現状、誰も何にも「気づけない」:

| 立場 | 今どうしているか | 問題 |
|---|---|---|
| 管理者 | 新規投稿はトップページを目視巡回 | 投稿に気づくのが遅れ、一次対応（7日目安 = moderation-policy.md）が守れなくなる |
| 投稿者 | 自分の投稿ページを再訪して確認 | ステータス変化・出版社コメントに気づけない（design.md §4-4） |
| 投稿者（削除時） | 管理者が手動でメール送信 | moderation-policy.md §33 の「削除時は投稿者へ通知」が手作業 |

## 2. プロバイダ選定

**【意見】Resend を推す。** 理由:

- 【事実】無料枠 3,000通/月・100通/日・ドメイン1つ（出典: https://resend.com/pricing 2026-07-15 確認）。本サイトの規模（当面は月数十通）に対して十分
- 【定石】Next.js / Vercel との統合実績が多く、公式 SDK（`resend` npm パッケージ）とドキュメントが簡潔。React Email でテンプレートをコンポーネント化する道もある
- 代替: Amazon SES（最安だが AWS アカウント・IAM 管理が増える）、SendGrid（無料枠 100通/日だが管理画面が重厚）。**どれでも要件は満たせる**ので、送信部分は `services/notification.ts` に隔離してプロバイダ差し替え可能にしておく

## 3. 段階導入 — ドメインの有無で Phase を切る

**【事実・設計の分岐点】Resend は独自ドメインを検証するまで、送信元 `onboarding@resend.dev` で「自分（Resend アカウント所有者）のメールアドレス宛」にしか送れない**（出典: https://resend.com/docs/knowledge-base/403-error-resend-dev-domain — "You can only send testing emails to your own email address"）。

つまり **管理者向け通知（宛先=自分）はドメインなしで今すぐ作れる**が、**投稿者向け通知（宛先=一般ユーザー）は独自ドメインの取得が前提**になる。

### Phase 1: 管理者向け通知（ドメイン不要・すぐ実装可）

- **イベント**: 新規投稿（`createReport` 成功後）
- **宛先**: 管理者のメールアドレス（= Resend アカウントのメール）
- 注意: `onboarding@resend.dev` はテスト用の送信元なので、これはあくまで暫定運用。Phase 2 でドメインを取ったら送信元を差し替える

### Phase 2: 投稿者向け通知（要・独自ドメイン取得）

- **イベント**:
  1. ステータス変化（`updateReport` で status が変わったとき）
  2. 出版社コメントの追加（同上で publisherComment が付いたとき。1と同時なら1通にまとめる）
  3. 投稿の削除（`deleteReport`。moderation-policy.md の手動送信を自動化）
- **宛先**: 投稿者（Report.user.email）
- **前提となるユーザー作業**: ドメイン取得（年千円台〜）→ Resend にドメイン追加 → DNS に SPF/DKIM レコード設定 → 検証
- 副産物: 取得したドメインは本体サイト（errata-hub.vercel.app → 独自ドメイン）にも使える

### Phase 3（将来・今回のスコープ外）

- 通報（Flag）実装時の管理者通知 — Phase 1 と同じ仕組みに乗るだけ
- アプリ内通知（ベル＋未読）— メール通知で十分か様子を見てから

## 4. アーキテクチャ

### 送信の呼び出し方: 「DB 書き込み成功後の fire-and-forget」

- Server Action / Route Handler の **DB 書き込みが成功した後**に送信する
- **送信失敗で本処理を失敗させない**（try/catch して `console.error` のみ）。画像削除の「DB 先行・Storage 失敗はログのみ」と同じ思想: 通知は本体（投稿・ステータス更新）の付随物であり、通知が落ちても本体の成立を妨げない
- リトライ・キューは v1 では作らない（【定石】月数十通の規模でキュー基盤は過剰。取りこぼしは Resend ダッシュボードの送信ログで確認できる）

### 置き場所: `src/services/notification.ts` 新設

```
services/notification.ts
  ├─ sendNewReportNotice(report)        … Phase 1
  ├─ sendStatusChangeNotice(report, before) … Phase 2
  └─ sendReportDeletedNotice(report)    … Phase 2
```

- Resend SDK の呼び出しはこのファイルに閉じ込める（プロバイダ差し替え・テストでのモックを楽にする）
- 既存の境界方針（design.md §7「データアクセスの境界」）に従い、アクション側は services の関数を呼ぶだけ

### 送らない条件（Phase 2 で必須のガード）

1. **退会者に送らない**: 退会者の email はダミー（`deleted-*@deleted.local`）なので送信自体が無意味＋バウンス源。`isWithdrawnEmail()`（lib/withdrawal.ts）で必ずスキップ
2. **オプトアウトを尊重**: 下記スキーマ参照
3. **自分の操作は自分に通知しない**: 管理者が自分の投稿のステータスを変えた場合など、操作者=宛先なら送らない

### テンプレート

- v1 は**プレーンテキスト**（React Email 等の HTML 化は必要になってから）。件名・本文は日本語
- 本文には投稿ページへの URL を含める（`https://errata-hub.vercel.app/reports/<id>`）

## 5. スキーマ変更

- **Phase 1: 変更なし**（宛先は管理者固定・オプトアウト不要）
- **Phase 2: Profile に1列追加**

```prisma
// 自分の投稿に関する通知メール（ステータス変化・出版社コメント・削除通知）の受信可否。
// オプトアウト方式（既定ON）。削除通知だけは規約運用上の必須連絡なのでこの設定に関わらず送る
notifyOnReportUpdate Boolean @default(true)
```

- 設定 UI は /account に トグルを1つ追加
- 【定石・法的整理】自分の投稿に対する対応結果の連絡はサービス運営上の連絡（トランザクションメール）であり、広告を含まなければ特定電子メール法の同意規制（オプトイン義務）の対象外。とはいえ受信者への配慮としてオプトアウトは付ける。**削除通知だけは例外的に常送**（moderation-policy.md の通知義務を優先）
- 通知ログのテーブルは**作らない**（Resend 側の送信ログで足りる。監査対象の管理操作は従来どおり AuditLog が持つ）

## 6. 環境変数と秘密の扱い

- `RESEND_API_KEY` を Vercel（Production / Preview）と `.env.local` に設定。**本番キーをローカルに置かない**運用は既存方針どおり（ローカルは自分宛テスト用に別キーを発行するか、送信部分をローカルでは no-op にする）
- 【定石】ローカル開発・ユニットテストでは実送信しない: `RESEND_API_KEY` 未設定なら送信をスキップして console.log に落とすフォールバックを入れる（e2e がメール送信で外部を叩かないためにも必要）

## 7. 実装順（承認後）

1. Phase 1: `services/notification.ts` + `createReport` へのフック + ユニットテスト（モック）— コード変更は小さく、スキーマ変更なし
2. （ユーザー作業）ドメイン取得 → Resend ドメイン検証
3. Phase 2: スキーマ1列追加（db push 必要）+ /account トグル + `updateReport` / `deleteReport` へのフック

## 8. ユーザーに決めてほしいこと

1. **プロバイダは Resend でよいか**（§2）
2. **Phase 1（管理者通知だけ先行）を進めてよいか** — Resend アカウント作成（無料・ユーザー作業）が前提
3. **独自ドメインを取るか**（Phase 2 の前提。サイト本体のドメインにもなる。維持費が恒久的に発生する点だけ留意）
