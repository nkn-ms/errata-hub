## ISBN は 10桁と13桁があり、正規化が必要

### 何が問題か

ISBN（本の識別番号）には2つの形式があり、**同じ1冊の本が両方の形式で表現できる**。

| 形式 | 桁数 | 例（同じ本） | 備考 |
|------|------|--------------|------|
| ISBN-10 | 10桁 | `4873116864` | 〜2006年。末尾が `X`（=10）のこともある |
| ISBN-13 | 13桁 | `9784873116860` | 2007年〜現在。先頭は `978` か `979` |

**移行時期**: ISBN-13 への切り替えは **2007年1月1日**。それより前に出版された本はおおむね ISBN-10、2007年以降は ISBN-13 が振られている。古い本を扱うと ISBN-10 が普通に出てくるので、両対応（=正規化）が必須。

ISBN-10 は「先頭に `978` を付けてチェック数字（末尾の検算用数字）を計算し直す」と ISBN-13 に変換できる。上の例の2つは**同じ本**。

そのため、文字列をそのまま突き合わせて名寄せすると：

- A さんが ISBN-13 `9784873116860` で投稿
- B さんが ISBN-10 `4873116864` で投稿

→ 文字列が違うので **同じ本が2レコードできてしまう**（＝二重化）。
DB に `@unique` を付けても、文字列が違えば別物扱いなので防げない。

### どう解決したか

**保存・照合の前に、必ず ISBN-13 に変換して統一（正規化）する。**
こうすれば同じ本は必ず同じ文字列になり、名寄せも `@unique` 制約も正しく効く。

- 正規化ロジック: [`src/utils/isbn.ts`](../src/utils/isbn.ts) の `toCanonicalIsbn(raw)`
  - ハイフン等を除去 → ISBN-10 なら ISBN-13 へ変換 → チェック数字を検証 → 不正なら `null`
- 投稿時に通す場所: [`src/app/api/feedbacks/route.ts`](../src/app/api/feedbacks/route.ts)（POST）
  - `toCanonicalIsbn` で正規化し、不正なら 400。`prisma.book.upsert({ where: { isbn } })` で名寄せ。
- DB: `Book.isbn` は **必須 + `@unique`**（ISBN-13 を保存）。

### 関連する方針

- 本の同一性は **ISBN を基準**にする。ISBN の無い本は投稿対象外（書籍検索の手動入力モードは廃止）。
- 将来 ISBN-10/13 以外の事情（洋書・電子のみ等）が出たら、この前提を見直す。

## 設計力の磨き方（role 設計の議論から）

### きっかけ

`role` に ADMIN/PUBLISHER/USER の3値を持たせていたが、`PUBLISHER` は
`PublisherAccess`（ユーザー×出版社の中間テーブル）があるかで導出できる重複状態だった。
結果 `role=PUBLISHER だが access ゼロ` のような「ズレ」が起きうる設計になっていた。
→ `role` は **ADMIN かどうか**だけにし、「出版社か」は access から導出する形へ。

### 大原則: 「何値の role にするか」ではなく「source of truth は何で、どのスコープに住むか」

ある値を `role` enum に入れてよいかは、次の5つを**全部**満たすかで判定する:

1. **排他的か** — 同時に1つだけか。「admin かつ editor」が成立するなら enum でなく集合（join table）。
2. **グローバルか** — リソースに紐づかないか。「org X の admin、org Y の member」ならスコープ付き → membership 側の role に置く。
3. **保存すべきか（導出できないか）** — 他の状態から計算できるなら保存しない。
4. **安定か** — 変更が意図的操作で、他の状態変化の副作用で勝手に変わらないか。
5. **実際に異なる権限を分岐させるか** — 各値が本当に違う振る舞いをゲートするか。

全部 YES なら3値以上の role が最適（例: ブログ CMS の reader/author/editor/admin）。
このアプリの `publisher` は #2(スコープ付き)・#3(導出可)・#5(何もゲートせず) で外れた。
**実装の良し悪しと無関係に、publisher は本質的にスコープ付き**なので global role の住人ではなかった。

### 日々の設計で効く習慣

1. **すべてのフィールドに「source of truth は？」と訊く。** 導出できるなら保存しない。派生状態の保存こそ全バグの母（drift）。
2. **「絡まってる」と感じたら直交軸を探す。** 8値ステータス = モデレーション状態 × 対応状態 の同居だった。混在概念の分解が設計の大半。
3. **不正な状態を“表現できなく”する。** `role=PUBLISHER かつ access ゼロ` は「不正だが表現可能」。導出にすれば表現不能になる。`isbn @unique` も同じ思想（DB 制約で illegal state を潰す）。
4. **名詞でなく動詞・ライフサイクルでモデルする。** 具体シナリオを状態遷移で再生すると設計の穴が出る（「ドメイン登録前に登録→後で追加→再ログイン」で drift を発見）。
5. **名前を正確につけ、現実と照合する。** Feedback→Report、`access の role=PUBLISHER` は名前自体が冗長を白状している。悪い名前は smell を隠し、正確な名前は smell を暴く。
6. **一流のスキーマを読む。** GitHub の権限 / Stripe / Discord・Linear の role を「なぜそうしたか」逆算して読む。

補足: enum role はやがて role→権限(RBAC)、さらに per-resource role / ポリシーエンジン(ABAC) へ育つことが多い。
「いつ卒業すべきか（複数同時 role・スコープ・細粒度権限が要る時）」を見極めるのも同じ筋肉。

## Supabase の anon キーと RLS（公開掲示板の admin 画面がリダイレクトした件から）

### きっかけ

ADMIN ロールのはずの自分が `/admin` を開くと `/` にリダイレクトされた。
DB を Prisma で確認すると `role = ADMIN` は正しく入っている。なのに弾かれる。
原因は **全テーブルで RLS が有効・かつ `Profile` にポリシーが1本も無い**状態だった。

### anon キーとは何か（危険な鍵ではなく「身分証」）

Supabase は作ったテーブルを **自動でインターネット上の REST API（PostgREST）として公開**する。
この API は **anon（publishable）キー**で叩け、このキーは `NEXT_PUBLIC_` で**ブラウザに配られる＝公開キー**。

一見「公開キーで DB を読み書きできる＝危険」に見えるが、誤解。
**anon キー単体は権限を持たない。「私は匿名の訪問者です」と名乗る身分証**でしかない。
（ログイン後はそのユーザーの JWT に変わり「この人です」と名乗る）
実際に何ができるかは **100% RLS が決める**。anon キーと RLS はワンセットで初めて意味を持つ。

### RLS とポリシー

| 用語 | 役割 |
|------|------|
| **RLS**（Row Level Security） | テーブルに**行単位**で鍵をかける機能。オンにした瞬間は**全拒否**がデフォルト |
| **ポリシー** | 「この条件の行は通してよい」という**許可ルール（合鍵）**。RLS と必ずセット |

- **RLS オフ** → 公開キーで誰でも全行読み書き可能（危険）。Supabase が「RLS 入れろ」と警告するのはこのため。
- **RLS オン＋ポリシー無し** → 公開裏口は**全拒否（施錠）**。安全だが Supabase クライアントからは何も読めない ← 今回これで proxy が詰まった。
- **RLS オン＋ポリシー** → 許可した行だけ通す。

ポリシー例（自分のプロフィール行だけ読めるようにする）:
```sql
CREATE POLICY "read own profile" ON "Profile"
  FOR SELECT USING (auth.uid() = id);
```

### なぜ Prisma は RLS に縛られず、Supabase クライアントは縛られたか

**同じ DB の同じ行でも、接続経路が違うと RLS の効き方が真逆になる**のが核心。

| | 経路 | RLS |
|---|------|-----|
| **Prisma** | 直接 Postgres 接続（特権ロール） | **バイパス**（無視） |
| **Supabase クライアント** | 公開 REST API（anon キー） | **従う** |

だから Prisma を使う `requireAdminPage`（レイアウト）は ADMIN を読めて、
Supabase クライアントを使う `proxy.ts` の Profile 読み取りだけが全拒否で弾かれた。

### 方針（このアプリでの結論）

このアプリは「ブラウザから DB を直接触らない」設計（→ 次項 BaaS vs バックエンド）。
よって **RLS は認可の主役ではなく、公開裏口(PostgREST)を塞ぐ「ロック」として全拒否のまま維持**する。
認可の主役はサーバー層（`services/auth.ts` の `requireAdmin` 系）。多層防御の最後の壁が RLS。
将来 SEO 等で「公開済みレポートだけ匿名読み取り可」にしたくなったら、その**1テーブルにだけ**読み取りポリシーを足す。

## BaaS モデル と バックエンドモデル

データの**守り方が根本的に違う**2つのアーキテクチャ。レストランのたとえが分かりやすい。

| | A. BaaS モデル（ビュッフェ） | B. バックエンドモデル（店員のいる店）← このアプリ |
|---|---|---|
| データに触るのは | ブラウザが**直接** Supabase | ブラウザ→**サーバー(Next.js)**→Prisma→DB |
| 誰が守るか | **RLS**（料理の周りのレール） | **サーバーのコード**（店員が判断） |
| 認可の書き場所 | SQL（ポリシー） | TypeScript（`requireAdmin` 等） |
| 向く用途 | 小〜中規模・バックエンド書きたくない | 複雑な認可・モデレーションがある |
| 例 | Firebase、本来の Supabase | 従来型 Web アプリ |

このアプリが **B を選ぶ理由**:
- 認可が複雑（ADMIN/一般、出版社メンバーシップ、将来のモデレーション）。これを全部 RLS ポリシー（SQL）で書くのは辛い。**TypeScript の方が読みやすくテストしやすい**。
- Supabase は「**Identity as a Service（認証係）**」として使い、DB は Prisma 経由でしか触らない。
- ポートフォリオとしても、サーバー層・サービス層をきれいに設計できる方が汎用的にアピールになる。

## エッジ / ミドルウェア(proxy.ts) と「ルート制御をどこに書くか」

### エッジ（edge）とは

クラウド事業者のネットワークの **\"端っこ\"＝ユーザーに物理的にいちばん近い場所**。
世界中にばらまかれたエッジサーバーで、リクエストが本体（ページ描画）に届く**前**に処理する。

```
ユーザー ──[エッジ：最寄りの関所]── … ── [中央サーバー(origin)：本体]
```

副作用として、エッジは**軽量・簡易な実行環境**で動くことが多い（エッジランタイム）。
→ **Prisma で DB に繋ぐような重い処理は不得意。だからミドルウェアで DB を読むのは筋が悪い。**

### proxy.ts とは

**Next.js のミドルウェア**（Next.js 16 で `middleware.ts` → `proxy.ts` に改名）。
全リクエストがページに届く前に横入りする**関所**。このアプリでの仕事:
1. **【本業】Supabase セッションの cookie 更新** — 認証トークンを裏で延長して cookie を書き戻す。Supabase 公式が「ミドルウェアでやれ」と指定する定番処理。
2. 保護ルート（`/submit`, `/admin`）への**未ログインアクセスを門前払い**。

### Next.js でルート制御をどこに書くか

App Router は **フォルダ構造そのものが経路**（React Router のような設定ファイルではない）。
`app/admin/page.tsx` → `/admin`。では構造で表せない／例外的な制御はどこに書くか。
**適用スコープの広さ別に置き場所が決まっている**（広い順）:

| 置き場所 | スコープ | 何を書くか | DBアクセス |
|---|---|---|---|
| **ミドルウェア**（`proxy.ts`） | 全リクエスト | ログイン有無の門前払い・リダイレクト・cookie更新。**軽く横断的**なもの | **しない**（エッジなので） |
| **`layout.tsx`** | その配下の全ページ | 「`/admin` 以下は全部ADMIN必須」等のまとまった守り＋共通UI | **してOK**（サーバーで動く） |
| **`page.tsx` / `route.ts`** | その1ページ/1API | 固有の条件分岐（`redirect()` / `notFound()`） | してOK |

**コツ: 必要範囲をカバーする一番狭い所に置く。重い判定（DB）は layout 以降に置く。**

admin への当てはめ（＝今回の設計判断）:
- **「ログインしてる？」**（軽い・横断的）→ **ミドルウェア(proxy.ts)**
- **「ADMINロール？」**（DBを読む）→ **`admin/layout.tsx`** で Prisma 判定（`requireAdminPage`）

不具合の元は、この「ADMINロール判定」を**間違ってミドルウェア側にも（Supabaseクライアントで）置いていた**こと。
判定を layout 一本に寄せるのが原則どおりの姿。

## 認証(AuthN) と 認可(AuthZ) は別物

英語の **\"auth\" は認証と認可の両方の略**として使われる紛らわしい語。実務では区別する:

| 略記 | 用語 | 日本語 | 問い | 例 |
|---|---|---|---|---|
| **AuthN** | Authentication | **認証** | あなたは**誰**？ | ログイン、`getUser()` |
| **AuthZ** | Authorization | **認可** | あなたは**何をしていい**？ | ADMINだけ削除可 |

覚え方: Auth**N** = w**h**o、Auth**Z** = what you're allowed。

- `services/auth.ts` の `auth` は、このアプリでは**認証も認可も両方**扱う（`getUser()`＝認証、`role==="ADMIN"`＝認可）。
- `admin` は「認可」という概念**ではなく**「**管理者という役割（ロール）**」の名前。認可の概念そのものは authorization。
  `requireAdmin` =「\"管理者ロール\"を持つか認可判定する関数」。

## 多層防御：layout のガードはキャッシュで古くなりうる（だから単独の砦にしない）

### 何が問題か

App Router の **部分レンダリング（partial rendering）** により、
**同じ layout を共有するページ間をクライアント側で移動しても、共有 layout は再実行されない**
（ページ部分だけ差し替わる）。さらにクライアントのルーターキャッシュが訪問済みルートを再利用することもある。

→ `admin/layout.tsx` の `requireAdminPage()` は「admin セクションに入った最初の1回」しか走らないことがあり、
その後の画面遷移では**再チェックされない**場合がある。

**問題シナリオ:**
1. ユーザー A は ADMIN。`/admin` を開く → layout が認可判定 → 通過 → 管理画面表示
2. その間に別の管理者が A を一般ユーザーに**降格**
3. A が「ユーザー管理」リンクをクリック → layout は再実行されず（＋キャッシュ）、
   **A はもう ADMIN でないのに管理UIが見え続ける**（＝表示の鮮度の問題）

### なぜ実害が出ないか＝多層防御の肝

A が実際に「削除」等の**操作**をすると、その処理（API Route / Server Action）が
**毎回サーバーで `requireAdmin()` を実行**する。これは**キャッシュされず最新 DB のロールを読む**ので、
**管理UIは見えても privileged な操作は必ず弾かれる（403）**。

### 守りの本丸はどこか

| 層 | 役割 | 鮮度 | 性質 |
|---|---|---|---|
| `proxy.ts`（ミドルウェア） | 未ログインの門前払い | 都度 | 粗いゲート |
| `admin/layout.tsx` | 管理UIを**表示**してよいか | **キャッシュされ得る（古くなる）** | UX・第一防衛線 |
| 各操作の `requireAdmin()`（API/Server Action） | **本当にその操作をしてよいか** | **都度・最新DB** | **真のセキュリティ境界** |

**結論: layout は「表示用ガード」でありキャッシュで古くなりうる。本当の境界は各操作ごとの `requireAdmin()`（毎回フレッシュ）。**
だから proxy のロール判定を消しても安全だった——セキュリティの本丸はもともと proxy でも layout でもなく、各操作の認可判定だから。

※ Next.js 16 はキャッシュ周りに breaking change あり。正確な staleTime が要るときは `node_modules/next/dist/docs/` を参照。

## オープンソースとセキュリティ（ケルクホフスの原則）

### 大原則

> **セキュリティは「コードを秘密にすること」に依存させてはいけない。「鍵(secret)を秘密にすること」に依存させる。**

これが **ケルクホフスの原則** ＝「隠すことによる安全（security through obscurity）は本物の安全ではない」。

- **コードは公開されても安全であるべき**。「コードを見られたら破られる」機能は**設計が悪い**サイン。リポジトリを隠すのではなく**設計を直す**。
- **本当に秘密にすべきは secret（鍵・パスワード・トークン）だけ**。コードではなく**環境変数／シークレットマネージャ**に置き、コミットしない。
- → secret さえ env に隔離していれば、**機能が何個増えてもコードは公開し続けられる**（将来 private 化を迫られない）。

### 公開キー と 秘密キー の区別

| 種類 | 例 | 置き場所 | 公開リポジトリで |
|---|---|---|---|
| **公開キー** | Supabase URL / anon(publishable) キー | `NEXT_PUBLIC_*`（ブラウザに配られる前提） | 漏れて困らない（守りは RLS。obscurity に頼らない） |
| **秘密キー** | Google Books APIキー、将来の Supabase service_role キー | サーバー側 env のみ。**`NEXT_PUBLIC_` を付けない** | 絶対にコミットしない |

### 「鍵を守る」と「機能を守る」は別物（両輪）

API キーをサーバーに隠すパターン（実際に GOOGLE_BOOKS_API_KEY でやったこと）:
1. env に置く（コードに書かない）→ 鍵が漏れない
2. `NEXT_PUBLIC_` を付けない → ブラウザJSに埋め込まれない（①だけでは不十分、②が抜けると漏れる）
3. `.gitignore` で `.env*` 除外 → コミット事故防止

これで「鍵の秘匿」は達成。だが**もう一つ**必要：

> 鍵を隠しても、その鍵を使う**エンドポイントに認可が無いと quota を使い込まれる**。
> → `/api/books/search` にログイン必須チェックを入れた（鍵を隠す＋エンドポイントも守る、の両輪）。

さらに多層防御として、Google Cloud Console 側で API キーにリファラ/IP/API種別の制限を掛けると、万一漏れても悪用されにくい（任意・後回し可）。

### md / ドキュメントの置き場所の慣習

- **ルート直下に置くもの**: `README.md`（GitHub の玄関・トップ表示）＋ `CLAUDE.md`/`AGENTS.md`（AIツールが規約上ルートから読む）。これらは場所が固定。
- **それ以外の読み物は `docs/` に寄せる**: 設計・要件・学習メモ・ER図など。
- ルートに作業メモや要件書を置くと public リポジトリで雑然と見える。`docs/` 集約が無難。
