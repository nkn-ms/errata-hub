## ISBN は 10桁と13桁があり、正規化が必要

### 何が問題か

ISBN（本の識別番号）には2つの形式があり、**同じ1冊の本が両方の形式で表現できる**。

| 形式 | 桁数 | 例（同じ本） | 備考 |
|------|------|--------------|------|
| ISBN-10 | 10桁 | `4873116864` | 〜2006年。末尾が `X`（=10）のこともある |
| ISBN-13 | 13桁 | `9784873116860` | 2007年〜現在。先頭は `978` か `979` |

**移行時期**: ISBN-13 への切り替えは **2007年1月1日**。それより前に出版された本はおおむね ISBN-10、2007年以降は ISBN-13 が振られている。古い本を扱うと ISBN-10 が普通に出てくるので、両対応（=正規化）が必須。

ISBN-10 は「先頭に `978` を付けてチェック数字（末尾の検算用数字）を計算し直す」と ISBN-13 に変換できる。上の例の2つは**同じ本**。

そのため、文字列をそのまま突き合わせて名寄せすると：

- A さんが ISBN-13 `9784873116860` で投稿
- B さんが ISBN-10 `4873116864` で投稿

→ 文字列が違うので **同じ本が2レコードできてしまう**（＝二重化）。
DB に `@unique` を付けても、文字列が違えば別物扱いなので防げない。

### どう解決したか

**保存・照合の前に、必ず ISBN-13 に変換して統一（正規化）する。**
こうすれば同じ本は必ず同じ文字列になり、名寄せも `@unique` 制約も正しく効く。

- 正規化ロジック: [`src/utils/isbn.ts`](../src/utils/isbn.ts) の `toCanonicalIsbn(raw)`
  - ハイフン等を除去 → ISBN-10 なら ISBN-13 へ変換 → チェック数字を検証 → 不正なら `null`
- 投稿時に通す場所: [`src/app/api/reports/route.ts`](../src/app/api/reports/route.ts)（POST。旧 `api/feedbacks` は Feedback→Report リネームで改称済み）
  - `toCanonicalIsbn` で正規化し、不正なら 400。`prisma.book.upsert({ where: { isbn } })` で名寄せ。
- DB: `Book.isbn` は **必須 + `@unique`**（ISBN-13 を保存）。

### 関連する方針

- 本の同一性は **ISBN を基準**にする。ISBN の無い本は投稿対象外（書籍検索の手動入力モードは廃止）。
- 将来 ISBN-10/13 以外の事情（洋書・電子のみ等）が出たら、この前提を見直す。

## 設計力の磨き方（role 設計の議論から）

### きっかけ

`role` に ADMIN/PUBLISHER/USER の3値を持たせていたが、`PUBLISHER` は
`PublisherAccess`（ユーザー×出版社の中間テーブル）があるかで導出できる重複状態だった。
結果 `role=PUBLISHER だが access ゼロ` のような「ズレ」が起きうる設計になっていた。
→ `role` は **ADMIN かどうか**だけにし、「出版社か」は access から導出する形へ。

### 大原則: 「何値の role にするか」ではなく「source of truth は何で、どのスコープに住むか」

ある値を `role` enum に入れてよいかは、次の5つを**全部**満たすかで判定する:

1. **排他的か** — 同時に1つだけか。「admin かつ editor」が成立するなら enum でなく集合（join table）。
2. **グローバルか** — リソースに紐づかないか。「org X の admin、org Y の member」ならスコープ付き → membership 側の role に置く。
3. **保存すべきか（導出できないか）** — 他の状態から計算できるなら保存しない。
4. **安定か** — 変更が意図的操作で、他の状態変化の副作用で勝手に変わらないか。
5. **実際に異なる権限を分岐させるか** — 各値が本当に違う振る舞いをゲートするか。

全部 YES なら3値以上の role が最適（例: ブログ CMS の reader/author/editor/admin）。
このアプリの `publisher` は #2(スコープ付き)・#3(導出可)・#5(何もゲートせず) で外れた。
**実装の良し悪しと無関係に、publisher は本質的にスコープ付き**なので global role の住人ではなかった。

### 日々の設計で効く習慣

1. **すべてのフィールドに「source of truth は？」と訊く。** 導出できるなら保存しない。派生状態の保存こそ全バグの母（drift）。
2. **「絡まってる」と感じたら直交軸を探す。** 8値ステータス = モデレーション状態 × 対応状態 の同居だった。混在概念の分解が設計の大半。
3. **不正な状態を“表現できなく”する。** `role=PUBLISHER かつ access ゼロ` は「不正だが表現可能」。導出にすれば表現不能になる。`isbn @unique` も同じ思想（DB 制約で illegal state を潰す）。
4. **名詞でなく動詞・ライフサイクルでモデルする。** 具体シナリオを状態遷移で再生すると設計の穴が出る（「ドメイン登録前に登録→後で追加→再ログイン」で drift を発見）。
5. **名前を正確につけ、現実と照合する。** Feedback→Report、`access の role=PUBLISHER` は名前自体が冗長を白状している。悪い名前は smell を隠し、正確な名前は smell を暴く。
6. **一流のスキーマを読む。** GitHub の権限 / Stripe / Discord・Linear の role を「なぜそうしたか」逆算して読む。

補足: enum role はやがて role→権限(RBAC)、さらに per-resource role / ポリシーエンジン(ABAC) へ育つことが多い。
「いつ卒業すべきか（複数同時 role・スコープ・細粒度権限が要る時）」を見極めるのも同じ筋肉。

## Supabase の anon キーと RLS（公開掲示板の admin 画面がリダイレクトした件から）

### きっかけ

ADMIN ロールのはずの自分が `/admin` を開くと `/` にリダイレクトされた。
DB を Prisma で確認すると `role = ADMIN` は正しく入っている。なのに弾かれる。
原因は **全テーブルで RLS が有効・かつ `Profile` にポリシーが1本も無い**状態だった。

### anon キーとは何か（危険な鍵ではなく「身分証」）

Supabase は作ったテーブルを **自動でインターネット上の REST API（PostgREST）として公開**する。
この API は **anon（publishable）キー**で叩け、このキーは `NEXT_PUBLIC_` で**ブラウザに配られる＝公開キー**。

一見「公開キーで DB を読み書きできる＝危険」に見えるが、誤解。
**anon キー単体は権限を持たない。「私は匿名の訪問者です」と名乗る身分証**でしかない。
（ログイン後はそのユーザーの JWT に変わり「この人です」と名乗る）
実際に何ができるかは **100% RLS が決める**。anon キーと RLS はワンセットで初めて意味を持つ。

### RLS とポリシー

| 用語 | 役割 |
|------|------|
| **RLS**（Row Level Security） | テーブルに**行単位**で鍵をかける機能。オンにした瞬間は**全拒否**がデフォルト |
| **ポリシー** | 「この条件の行は通してよい」という**許可ルール（合鍵）**。RLS と必ずセット |

- **RLS オフ** → 公開キーで誰でも全行読み書き可能（危険）。Supabase が「RLS 入れろ」と警告するのはこのため。
- **RLS オン＋ポリシー無し** → 公開裏口は**全拒否（施錠）**。安全だが Supabase クライアントからは何も読めない ← 今回これで proxy が詰まった。
- **RLS オン＋ポリシー** → 許可した行だけ通す。

ポリシー例（自分のプロフィール行だけ読めるようにする）:
```sql
CREATE POLICY "read own profile" ON "Profile"
  FOR SELECT USING (auth.uid() = id);
```

### anon(publishable) キー と service_role(secret) キーは「正反対」

anon キーを「強い鍵」と誤解しやすいが、**service_role キーこそが本物の強い鍵**で、両者は対極にある。

| | anon / publishable | service_role / secret |
|---|---|---|
| 性質 | **公開キー**（ブラウザ配布OK） | **秘密キー**（サーバー専用・絶対非公開） |
| 権限 | ほぼ無力。「匿名訪問者」の**身分証**だけ | **全能(god mode)**。DB も Auth Admin API も何でも |
| RLS | **従う**（できることは RLS が決める） | **完全バイパス**（RLS を無視して全行操作） |
| 置き場所 | `NEXT_PUBLIC_*`（埋め込みOK） | サーバー側 env のみ。**`NEXT_PUBLIC_` を付けない** |
| 新名称 | `sb_publishable_...` | `sb_secret_...` |
| たとえ | 入館証（中身は RLS の鍵次第） | **マスターキー（全部屋開く）** |

- **anon が公開でも安全なのは RLS が守るから**（上記の通り）。**service_role は RLS を素通り**するので、漏れたら DB 全体を読み書きされる＝root パスワード並みの管理が必要。
- 用途例：管理者のパスワードを忘れた時、ダッシュボードに「直接パスワード設定」欄が無い版では、**service_role(secret) キーで `auth.admin.updateUserById(uid, { password })`** を一度だけ実行して上書きできる（使い終わったら env から即削除）。anon キーではこの管理操作は不可（権限が無い）。

### なぜ Prisma は RLS に縛られず、Supabase クライアントは縛られたか

**同じ DB の同じ行でも、接続経路が違うと RLS の効き方が真逆になる**のが核心。

| | 経路 | RLS |
|---|------|-----|
| **Prisma** | 直接 Postgres 接続（特権ロール） | **バイパス**（無視） |
| **Supabase クライアント** | 公開 REST API（anon キー） | **従う** |

だから Prisma を使う `requireAdminPage`（レイアウト）は ADMIN を読めて、
Supabase クライアントを使う `proxy.ts` の Profile 読み取りだけが全拒否で弾かれた。

### 方針（このアプリでの結論）

このアプリは「ブラウザから DB を直接触らない」設計（→ 次項 BaaS vs バックエンド）。
よって **RLS は認可の主役ではなく、公開裏口(PostgREST)を塞ぐ「ロック」として全拒否のまま維持**する。
認可の主役はサーバー層（`services/auth.ts` の `requireAdmin` 系）。多層防御の最後の壁が RLS。
将来 SEO 等で「公開済みレポートだけ匿名読み取り可」にしたくなったら、その**1テーブルにだけ**読み取りポリシーを足す。

## BaaS モデル と バックエンドモデル

データの**守り方が根本的に違う**2つのアーキテクチャ。レストランのたとえが分かりやすい。

| | A. BaaS モデル（ビュッフェ） | B. バックエンドモデル（店員のいる店）← このアプリ |
|---|---|---|
| データに触るのは | ブラウザが**直接** Supabase | ブラウザ→**サーバー(Next.js)**→Prisma→DB |
| 誰が守るか | **RLS**（料理の周りのレール） | **サーバーのコード**（店員が判断） |
| 認可の書き場所 | SQL（ポリシー） | TypeScript（`requireAdmin` 等） |
| 向く用途 | 小〜中規模・バックエンド書きたくない | 複雑な認可・モデレーションがある |
| 例 | Firebase、本来の Supabase | 従来型 Web アプリ |

このアプリが **B を選ぶ理由**:
- 認可が複雑（ADMIN/一般、出版社メンバーシップ、将来のモデレーション）。これを全部 RLS ポリシー（SQL）で書くのは辛い。**TypeScript の方が読みやすくテストしやすい**。
- Supabase は「**Identity as a Service（認証係）**」として使い、DB は Prisma 経由でしか触らない。
- ポートフォリオとしても、サーバー層・サービス層をきれいに設計できる方が汎用的にアピールになる。

## エッジ / ミドルウェア(proxy.ts) と「ルート制御をどこに書くか」

### エッジ（edge）とは

クラウド事業者のネットワークの **\"端っこ\"＝ユーザーに物理的にいちばん近い場所**。
世界中にばらまかれたエッジサーバーで、リクエストが本体（ページ描画）に届く**前**に処理する。

```
ユーザー ──[エッジ：最寄りの関所]── … ── [中央サーバー(origin)：本体]
```

副作用として、エッジは**軽量・簡易な実行環境**で動くことが多い（エッジランタイム）。
→ **Prisma で DB に繋ぐような重い処理は不得意。だからミドルウェアで DB を読むのは筋が悪い。**

### proxy.ts とは

**Next.js のミドルウェア**（Next.js 16 で `middleware.ts` → `proxy.ts` に改名）。
全リクエストがページに届く前に横入りする**関所**。このアプリでの仕事:
1. **【本業】Supabase セッションの cookie 更新** — 認証トークンを裏で延長して cookie を書き戻す。Supabase 公式が「ミドルウェアでやれ」と指定する定番処理。
2. 保護ルート（`/submit`, `/admin`）への**未ログインアクセスを門前払い**。

### Next.js でルート制御をどこに書くか

App Router は **フォルダ構造そのものが経路**（React Router のような設定ファイルではない）。
`app/admin/page.tsx` → `/admin`。では構造で表せない／例外的な制御はどこに書くか。
**適用スコープの広さ別に置き場所が決まっている**（広い順）:

| 置き場所 | スコープ | 何を書くか | DBアクセス |
|---|---|---|---|
| **ミドルウェア**（`proxy.ts`） | 全リクエスト | ログイン有無の門前払い・リダイレクト・cookie更新。**軽く横断的**なもの | **しない**（エッジなので） |
| **`layout.tsx`** | その配下の全ページ | 「`/admin` 以下は全部ADMIN必須」等のまとまった守り＋共通UI | **してOK**（サーバーで動く） |
| **`page.tsx` / `route.ts`** | その1ページ/1API | 固有の条件分岐（`redirect()` / `notFound()`） | してOK |

**コツ: 必要範囲をカバーする一番狭い所に置く。重い判定（DB）は layout 以降に置く。**

admin への当てはめ（＝今回の設計判断）:
- **「ログインしてる？」**（軽い・横断的）→ **ミドルウェア(proxy.ts)**
- **「ADMINロール？」**（DBを読む）→ **`admin/layout.tsx`** で Prisma 判定（`requireAdminPage`）

不具合の元は、この「ADMINロール判定」を**間違ってミドルウェア側にも（Supabaseクライアントで）置いていた**こと。
判定を layout 一本に寄せるのが原則どおりの姿。

### matcher は「静的アセット以外の全ルート」にする（2026-07 監査で修正）

当初 matcher を保護ルート（`/admin`・`/submit`）に限定していたが、これは落とし穴だった。
Supabase のセッション維持は「短命のアクセストークンを裏でリフレッシュ（延長）し、**その結果を cookie に書き戻す**」ことで成り立つが、**cookie に書き戻せるのは実質ミドルウェアだけ**（Server Component は cookie を書けない。`lib/supabase/server.ts` の setAll が失敗を握りつぶしているのはそのため）。
→ matcher が狭いと、公開ページだけを閲覧しているログインユーザーはトークン延長が保存されず、時間経過で突然ログアウトされ得る。
→ Supabase 公式推奨どおり、**除外型 matcher（静的ファイルだけ除外して全ルートで実行）**に修正。未ログイン訪問者は auth cookie が無く `getUser()` はネットワークを叩かず即 null を返すため、匿名アクセスへのコストはほぼ無い。
出典: https://supabase.com/docs/guides/auth/server-side/nextjs

## なぜトークンが2本あるのか（アクセストークン=JWT と リフレッシュトークン）

### 前提: ログイン状態の維持には2方式ある

| 方式 | 仕組み | 長所 | 短所 |
|---|---|---|---|
| **サーバーセッション** | ランダムなセッションIDを cookie に。毎リクエスト、サーバーがDBで照合 | 即座に失効させられる | **毎リクエストDB参照**（遅い・認証サーバーが単一障害点） |
| **JWT（自己完結トークン）** | 「私はユーザーX」という署名付きの証明書を cookie に。サーバーは**署名検証だけ**で信用 | DB参照ゼロ・どのサーバーでも検証可能 | **失効させられない**（発行後は期限切れまで有効） |

**JWT (JSON Web Token)** = 「ヘッダ.本文.署名」の3部構成の文字列。本文（ユーザーID等）は base64 で誰でも読めるが、
発行者（Supabase Auth）の鍵による**署名**があるため改竄・偽造はできない。「読める・でも書き換えられない身分証」。

### 2本立ては「両方式のいいとこ取り」

JWT の「失効させられない」弱点は、**寿命を短くする**（Supabase 既定 約1時間）ことで緩和できる。
だが短命だと1時間ごとに再ログインが必要になる。そこで:

| | アクセストークン（JWT） | リフレッシュトークン |
|---|---|---|
| 役割 | 毎リクエストの身分証明 | 新しいアクセストークンをもらう引換券 |
| 寿命 | 短い（〜1時間） | 長い（ログイン状態が続く限り） |
| 検証方法 | **署名検証のみ**（DB参照なし・速い） | **サーバーがDBで照合**（使うのは1時間に1回だけなので遅くても良い） |
| 盗まれたら | 最大1時間で自然失効 | **サーバー側で失効させられる**＋使い捨てローテーション（使用済みの再利用を検知したら家族ごと無効化） |

つまり「高速な検証（JWT）を日常に、失効可能な照合（リフレッシュ）を低頻度に」という役割分担。
Supabase では PostgREST が JWT の中身（`auth.uid()`）で RLS を判定するのも「DB参照なしで検証できる」JWT の性質に乗っている。

### このアプリでの実務ポイント

- リフレッシュの実行と cookie への保存はミドルウェア（`proxy.ts`）の `getUser()` が担う（前項）。
- JWT の本文は読める（`iss` = 発行者などが見える）が秘密ではない。秘密は**署名鍵**の側。

### トークンが盗まれたらどうなるか

- **アクセストークン**: 「盗まれても安全」ではない。失効させる手段が無く、残り寿命（最大1時間）の間は攻撃者が本人として振る舞える。正確には「**被害時間に上限がある**」（だから寿命を短くしている）。
- **リフレッシュトークン**: 盗まれたとき最も危険。守りは三層:
  1. そもそも盗みにくい — httpOnly cookie（JSから読めない＝XSSで直接盗めない）＋HTTPS。盗むには端末乗っ取り級の侵害が要る。
  2. **ローテーション＋再利用検知** — 1回使い切りなので、攻撃者が使うと本人側の手元のトークンが「使用済み」になる。本人の次回アクセスで再利用を検知し、**トークンファミリー**（ログイン1回から親→子→孫と連なるトークンの系譜。英語の refresh token family）を丸ごと無効化＝攻撃者も強制ログアウト。つまり本人が使い続けている限り盗難は自動発覚する。
  3. 絶対期限・不活性タイムアウト — 本人が**二度とアクセスしない**場合は 2 が発動せず攻撃者が居座れる。これを塞ぐのが期限側の守り（Supabase では不活性タイムアウトは有料プラン機能。本アプリは未使用＝端末乗っ取り前提の攻撃シナリオと扱うデータの機微度から許容と判断・2026-07-10）。
- 実際の盗難ではアクセス/リフレッシュは同じ cookie 領域にあり**同時に盗まれる**ことが多い。その時の本命の守りが 2。
- 寿命の相場: アクセストークンは 5分〜1時間（1時間が中心・金融系は5〜15分）、リフレッシュは数日〜90日＋ローテーション、または無期限＋不活性タイムアウト。参考: OWASP（Webアプリセキュリティの国際非営利団体。Top 10 と Cheat Sheet Series が事実上の標準リファレンス）の Session Management Cheat Sheet。

## 認証(AuthN) と 認可(AuthZ) は別物

英語の **\"auth\" は認証と認可の両方の略**として使われる紛らわしい語。実務では区別する:

| 略記 | 用語 | 日本語 | 問い | 例 |
|---|---|---|---|---|
| **AuthN** | Authentication | **認証** | あなたは**誰**？ | ログイン、`getUser()` |
| **AuthZ** | Authorization | **認可** | あなたは**何をしていい**？ | ADMINだけ削除可 |

覚え方: Auth**N** = w**h**o、Auth**Z** = what you're allowed。

- `services/auth.ts` の `auth` は、このアプリでは**認証も認可も両方**扱う（`getUser()`＝認証、`role==="ADMIN"`＝認可）。
- `admin` は「認可」という概念**ではなく**「**管理者という役割（ロール）**」の名前。認可の概念そのものは authorization。
  `requireAdmin` =「\"管理者ロール\"を持つか認可判定する関数」。

## 多層防御：layout のガードはキャッシュで古くなりうる（だから単独の砦にしない）

### 何が問題か

App Router の **部分レンダリング（partial rendering）** により、
**同じ layout を共有するページ間をクライアント側で移動しても、共有 layout は再実行されない**
（ページ部分だけ差し替わる）。さらにクライアントのルーターキャッシュが訪問済みルートを再利用することもある。

→ `admin/layout.tsx` の `requireAdminPage()` は「admin セクションに入った最初の1回」しか走らないことがあり、
その後の画面遷移では**再チェックされない**場合がある。

**問題シナリオ:**
1. ユーザー A は ADMIN。`/admin` を開く → layout が認可判定 → 通過 → 管理画面表示
2. その間に別の管理者が A を一般ユーザーに**降格**
3. A が「ユーザー管理」リンクをクリック → layout は再実行されず（＋キャッシュ）、
   **A はもう ADMIN でないのに管理UIが見え続ける**（＝表示の鮮度の問題）

### なぜ実害が出ないか＝多層防御の肝

A が実際に「削除」等の**操作**をすると、その処理（API Route / Server Action）が
**毎回サーバーで `requireAdmin()` を実行**する。これは**キャッシュされず最新 DB のロールを読む**ので、
**管理UIは見えても privileged な操作は必ず弾かれる（403）**。

### 守りの本丸はどこか

| 層 | 役割 | 鮮度 | 性質 |
|---|---|---|---|
| `proxy.ts`（ミドルウェア） | 未ログインの門前払い | 都度 | 粗いゲート |
| `admin/layout.tsx` | 管理UIを**表示**してよいか | **キャッシュされ得る（古くなる）** | UX・第一防衛線 |
| 各操作の `requireAdmin()`（API/Server Action） | **本当にその操作をしてよいか** | **都度・最新DB** | **真のセキュリティ境界** |

**結論: layout は「表示用ガード」でありキャッシュで古くなりうる。本当の境界は各操作ごとの `requireAdmin()`（毎回フレッシュ）。**
だから proxy のロール判定を消しても安全だった——セキュリティの本丸はもともと proxy でも layout でもなく、各操作の認可判定だから。

※ Next.js 16 はキャッシュ周りに breaking change あり。正確な staleTime が要るときは `node_modules/next/dist/docs/` を参照。

## オープンソースとセキュリティ（ケルクホフスの原則）

### 大原則

> **セキュリティは「コードを秘密にすること」に依存させてはいけない。「鍵(secret)を秘密にすること」に依存させる。**

これが **ケルクホフスの原則** ＝「隠すことによる安全（security through obscurity）は本物の安全ではない」。

- **コードは公開されても安全であるべき**。「コードを見られたら破られる」機能は**設計が悪い**サイン。リポジトリを隠すのではなく**設計を直す**。
- **本当に秘密にすべきは secret（鍵・パスワード・トークン）だけ**。コードではなく**環境変数／シークレットマネージャ**に置き、コミットしない。
- → secret さえ env に隔離していれば、**機能が何個増えてもコードは公開し続けられる**（将来 private 化を迫られない）。

### 公開キー と 秘密キー の区別

| 種類 | 例 | 置き場所 | 公開リポジトリで |
|---|---|---|---|
| **公開キー** | Supabase URL / anon(publishable) キー | `NEXT_PUBLIC_*`（ブラウザに配られる前提） | 漏れて困らない（守りは RLS。obscurity に頼らない） |
| **秘密キー** | Google Books APIキー、Supabase secret キー（退会機能の admin 操作で使用） | サーバー側 env のみ。**`NEXT_PUBLIC_` を付けない** | 絶対にコミットしない |

### 「鍵を守る」と「機能を守る」は別物（両輪）

API キーをサーバーに隠すパターン（実際に GOOGLE_BOOKS_API_KEY でやったこと）:
1. env に置く（コードに書かない）→ 鍵が漏れない
2. `NEXT_PUBLIC_` を付けない → ブラウザJSに埋め込まれない（①だけでは不十分、②が抜けると漏れる）
3. `.gitignore` で `.env*` 除外 → コミット事故防止

これで「鍵の秘匿」は達成。だが**もう一つ**必要：

> 鍵を隠しても、その鍵を使う**エンドポイントに認可が無いと quota を使い込まれる**。
> → `/api/books/search` にログイン必須チェックを入れた（鍵を隠す＋エンドポイントも守る、の両輪）。

さらに多層防御として、Google Cloud Console 側で API キーにリファラ/IP/API種別の制限を掛けると、万一漏れても悪用されにくい（任意・後回し可）。

### md / ドキュメントの置き場所の慣習

- **ルート直下に置くもの**: `README.md`（GitHub の玄関・トップ表示）＋ `CLAUDE.md`/`AGENTS.md`（AIツールが規約上ルートから読む）。これらは場所が固定。
- **それ以外の読み物は `docs/` に寄せる**: 設計・要件・学習メモ・ER図など。
- ルートに作業メモや要件書を置くと public リポジトリで雑然と見える。`docs/` 集約が無難。

## 外部キーの onDelete（Cascade / Restrict / SetNull）と、auth.users と Profile を「あえて分離」する設計

### きっかけ

ADMIN アカウントのパスワードを忘れた。「削除して作り直すのが筋か？」を検討する中で、
**親レコードを消すと子レコードがどうなるか**（＝外部キーの削除時挙動）を整理した。

### 外部キーの onDelete とは

子テーブルが親を参照しているとき、**親が消えたら子をどうするか**を DB に宣言する設定。

| 挙動 | 意味 | このアプリの例 |
|------|------|----------------|
| **Cascade** | 親を消すと子も**自動で芋づる削除** | `ReportImage`→`Report`、`PublisherAccess`→`Profile` |
| **Restrict**（Prisma の必須リレーション既定） | 子が残っている親は**削除を拒否**（ブロック） | `Report`→`Profile`（onDelete 未指定＝Restrict） |
| **SetNull** | 親を消すと子の外部キーを `null` に | （今回は不採用。`Report.userId` は必須なので使えない） |

➡️ つまり `Report` を持つ `Profile` は **Restrict のせいでそもそも削除できない**（DB がブロック）。
「ユーザーを消したらレポートが消える」のではなく「**レポートがある限りユーザーを消せない**」が正しい。

### `auth.users` と `Profile` を「あえて分離」している設計

このアプリの肝。Supabase **Auth**（`auth.users`：ログイン情報）と Prisma の **`Profile`**（アプリ内ユーザー）は、
`Profile.id` に同じ UUID を**コピーして持つだけで、auth への外部キーは張っていない**。
スキーマのコメントに意図が明記：「auth.users 削除後も操作履歴を追跡するための記録用」。

→ **「auth ユーザー削除」≠「Profile 削除」**。auth を消しても `Profile`/`Report` は**消えずに孤立**する（=カスケードしない）。

### 落とし穴：同じメールで「再登録」すると壊れる

再登録すると Supabase は**新しい UUID** で auth ユーザーを作る。callback は
`upsert({ where:{ id:新UUID }, create:{ id:新UUID, email:同じメール } })` を実行するが、
upsert は **id で判定**するので create に進む → ところが `Profile.email` は **@unique**、
孤児になった旧 Profile が同じメールを握ったまま → **ユニーク制約違反で Profile 作成に失敗**。
結果「**ログインはできるが Profile が無い**」壊れた状態になり、`findUnique` が null を返して管理画面等が崩れる。
さらに新アカウントは別人扱いで role は USER に逆戻り（ADMIN 喪失）。

### 教訓

- **削除より状態変更を優先する**。パスワード忘れは「再設定」で済み、削除＝孤児掃除＋メール衝突回避＋権限再付与の手作業が必ず出る。
- **認証(identity)とアプリ内ユーザー(profile)を分離**すると、退会後もコンテンツ・監査を保てる柔軟性が出る（次項の匿名化が可能になる）。代償として「再登録時のメール衝突」を自分で面倒見る必要がある。

## アカウント列挙(account enumeration)対策とパスワードの不可逆ハッシュ

### きっかけ

ログインでメアド/パスワードのどちらか一方だけ違うとき、エラー文言をどう出すか相談した。

### 大原則：エラーで「登録の有無」を漏らさない

> ログイン失敗は **どちらが違うか・そのメールが登録済みかを明かさない**汎用文言にする。

- ✅ 「メールアドレスまたはパスワードが正しくありません」
- ❌ 「このメールは登録されていません」「パスワードが違います」

「登録されていません」は親切に見えて、**アカウント列挙攻撃**を許す。攻撃者がメアドを総当たりして
「どれが登録済みか」を判別でき、標的型フィッシングやパスワードリスト攻撃の下準備になる（OWASP 推奨も汎用文言）。
**親切さはエラー文言を弱めるのではなく、「パスワードをお忘れですか？」リンク＋再発行フローで担保**する。
列挙対策は login だけでなく **signup（「既に登録済み」を出さない）・パスワード再発行（「登録があれば送信しました」）でも一貫**させて初めて効く。

### パスワードは「復元」できない（ハッシュ）

パスワードは平文では保存されず、**一方向ハッシュ**（bcrypt/argon 等）で保存される。
ハッシュは「元に戻せない」前提の変換なので、**運営者でもダッシュボードでも誰も平文を取り出せない**（これが正しい設計）。
だから「パスワード教えて」は原理的に不可能で、忘れたら**新しい値に再設定**するしかない。

## GDPR の「消去権」は匿名化で満たせる（退会＝物理削除ではなく PII スクラブ）

### 用語（先に定義）

- **PII**（Personally Identifiable Information／個人を特定できる情報）：単体や組合せで「誰か」を特定できる情報。例：メール・氏名。このアプリでは `email` と `displayName`。
- **スクラブ(scrub／こすり落とす)**：レコードを消さず、**中の機微な値だけ上書き・消去**して個人を特定不能にすること（データ洗浄）。

### きっかけ

「退会したらレポートは消える？残す？」の設計議論。公開掲示板なのでレポート＝コミュニティ資産。

### 大原則：消すのは「個人データ」であって「コンテンツ」ではない

GDPR の消去権が対象とするのは **PII**。**匿名化して個人と結びつかなくなったデータは GDPR の対象外**になる。
→ 退会では **PII だけ消し、コンテンツ（レポート）は匿名で残せる**。これが UGC（ユーザー投稿）サービスの定石。

### このアプリの退会方針（実装済: `app/actions/auth.ts` の `withdraw`）

1. `auth.users` を Admin API で削除（**auth 側 PII** ＝メール/メタデータとログイン情報を消す）
2. `Profile` は**消さず PII だけスクラブ**：`email`→匿名ダミー（@unique+必須なので null 不可）、`displayName`→null（UI で「退会済みユーザー」表示）
3. `Report` はそのまま保全 → 投稿者欄は「退会済みユーザー」

「レポートの論理削除」ではなく**投稿者の匿名化**なので、確定方針「論理削除は不採用・物理削除＋AuditLog」とも矛盾しない。
管理者によるレポート削除（モデレーション）は従来どおり**物理削除＋AuditLog**で別系統。

## レスポンシブ：Tailwind のブレークポイントは標準値・据え置き（対応はコンポーネント単位）

### きっかけ

「画面サイズの区切りは何種類で、どの値で、根拠は？」という疑問。確認すると **カスタム定義は無く Tailwind 標準値をそのまま使用**していた（`globals.css` の `@theme` は色とフォントのみ・`tailwind.config` ファイルも無し）。実際にコードで使っているのは `sm:` と `lg:` がほとんど。

### Tailwind 標準ブレークポイント（v4・すべて min-width＝モバイルファースト）

| 接頭辞 | 効き始める幅 | だいたいの端末 |
|--------|--------------|----------------|
| (無印) | 0px〜 | 全幅（まずスマホ前提で書く） |
| `sm:` | **≥640px** | 大きめスマホ横〜小型タブレット |
| `md:` | ≥768px | タブレット |
| `lg:` | **≥1024px** | ノートPC |
| `xl:` | ≥1280px | デスクトップ |
| `2xl:` | ≥1536px | 大型モニタ |

`min-width`（下限）の積み上げ式。「無印＝全サイズに適用」「`sm:`＝640px以上で上書き」。例 `hidden sm:block`＝「640px未満は非表示・以上で表示」。`max-w-screen-2xl` はコンテナ幅の上限（1536px）で、ブレークポイント接頭辞とは別物。

### 根拠と方針

- これらは**意図的に選んだ値ではなく Tailwind 標準を継承**したもの。だが標準値は一般用途向けに練られた**業界標準**でサニティとして適切。**あえて数値を変える必要はない**（カスタムは認知コストが増えるだけになりがち）。
- 大事な考え方：**効くのは「breakpoint の数値を変える」ことではなく「自分のレイアウトが実際に崩れる所で対応する」こと**。breakpoint は“端末幅”基準だが、理想は“**コンテンツが崩れる幅**”基準。
  - 例：モバイルでテーブルが横溢れ（≈390px で崩れる）は `sm`(640px) より下＝**全スマホで崩れている**問題。これは breakpoint の値が悪いのではなく、**テーブルに小画面用の作り（カード型など）を入れる**べき、という話。
- **方針：数値は標準のまま据え置き。レスポンシブ対応は「崩れるコンポーネント単位」で行う。** どうしてもスマホをさらに細分化したくなったら v4 では `@theme { --breakpoint-xs: 480px; }` で追加可能（現状不要）。

## link と button は「見た目」でなく「挙動」で選ぶ（投稿するボタンが Link な理由）

「投稿する」はボタンの見た目なのに実装は `<Link>`、ログアウトはテキストの見た目なのに `<button>` — 一見ちぐはぐだが、これは Web 標準・アクセシビリティのベストプラクティス。

- **原則: URL が変わるだけなら `<a>`（link）、状態を変えるなら `<button>`。** 見た目（青い塗り・角丸）は CSS の関心事で、要素の選択には関与させない。
- link であるメリット: Cmd+クリックで新規タブ、右クリックでURLコピー、ホバーで遷移先表示、Next.js `<Link>` の prefetch。`button + router.push` にするとこれらを全部失う。
- 逆にログアウトを `<a href="/logout">` にすると **GET で状態変更**することになり、ブラウザの prefetch やクローラーが URL を踏んだだけで勝手にログアウトする事故が起きる（有名なやらかしパターン）。スクリーンリーダーも「link=どこかへ飛ぶ / button=何かが起きる」と読み分けるため、入れ替えはユーザーを騙す。
- 実例: GitHub ヘッダーの「New repository」（緑ボタン）は `<a>`、ログアウトは `<form>`+`<button>`。shadcn/ui はこの用途に `<Button asChild><Link …>` という API を持つ。
- 本プロジェクトの実装（header-nav.tsx の「投稿する」= Link にボタン風スタイル / ログアウト = button）は正しい。違和感の解消は実装の入れ替えではなく「見た目を挙動に寄せる」方向で行う（例: cursor-pointer の一括適用）。

## user_metadata は「認証ユーザーに付く自由記入のJSONメモ欄」— 表示名の正にはしない

Supabase Auth のユーザー本体（`auth.users`）には認証に必要な情報（メール・パスワードハッシュ・確認日時など）が入っている。その横に付いている**自由記入の JSON 欄**が `user_metadata`（DB カラム名は `raw_user_meta_data`）。中身のスキーマは決まっておらず、書き込むのは主に次の2者。

| 誰が | いつ | 何が入るか |
|------|------|-----------|
| アプリ | 会員登録時（`signUp` の `options.data`）や `updateUser` | 登録フォームの表示名など任意の値 |
| OAuth プロバイダ | GitHub ログイン時に**自動で** | GitHub プロフィール（`user_name`・`avatar_url`・`email` など） |

参考: https://supabase.com/docs/guides/auth/managing-user-data

### 注意点（権限判断に使わない）

`user_metadata` は**本人がクライアント API（`updateUser`）から自由に書き換えられる**。「管理者かどうか」のような権限判断に使うと自己昇格できてしまうため絶対に使わない。本プロジェクトで `role` を Profile テーブル（サーバー管理）に持つのはこのため。なお管理者しか書けない `app_metadata` という別領域もあるが、本プロジェクトでは未使用。

### 本プロジェクトでの方針（2026-07-09 確定）

**表示名の正は `Profile.displayName` のみ。`user_metadata.display_name` は「会員登録フォーム → メール確認後の callback で Profile を作る」までの一度きりの運搬役で、以後は参照も同期もしない。**

かつては「Profile が正・user_metadata も整合のため合わせて更新する」という二重管理だったが、ログイン経路（メール登録・GitHub・将来の Google）が増えるたびに同期漏れが起きる構造で、実際に GitHub ログインでヘッダーがメール表示になるバグが出た（GitHub 由来の metadata には `display_name` というキーが無いため）。読む場所を Profile に一本化して同期コード自体を廃止した（コミット b1492de）。

## Next.js の `metadata` / `generateMetadata` は「予約 export」— 呼び出しコードはどこにも無い

### きっかけ

「`/users/[id]` だけブラウザのタブ表示が『Errata Hub』のままなのはなぜか」を調べた際の疑問。「`metadata` は各ページで明示的に呼ばれているのか？ grep しても呼び出しが見当たらない」→ **見つからないのが正解**で、どこにも呼び出しコードは存在しない。

### 「フレームワークがあなたのファイルを呼ぶ」構造（規約ベース）

App Router は「アプリのコードがフレームワークを呼ぶ」のではなく、**フレームワークが決まった場所・決まった名前の export を探して呼ぶ**（いわゆる規約ベース convention-based）。ルートを描画するとき Next.js が `page.tsx` / `layout.tsx` から探しに行く「予約 export」の代表：

| export 名 | Next.js がやること |
|-----------|--------------------|
| `default`（ページ/レイアウト本体） | ページの中身として描画 |
| `metadata`（オブジェクト・静的） | `<head>` 内の `<title>` や `<meta>` を生成 |
| `generateMetadata`（関数・動的） | 描画前に実行し、返り値から同じく `<head>` を生成 |

考えてみればページコンポーネント自体も同じで、`page.tsx` の `export default` を import して呼んでいるコードは無い。ファイル配置（`app/reports/[id]/page.tsx` という置き場所）を見て Next.js が勝手に呼んでいる。`metadata` / `generateMetadata` はその予約名の仲間。

### 静的 `metadata` と動的 `generateMetadata` の使い分け

- `export const metadata = {...}` — **静的**。ビルド時に決まる固定値。本プロジェクトでは `app/layout.tsx` がサイト全体のデフォルト（`title: "Errata Hub"` ＋公開前の一時的な `robots: noindex`）を持つ。
- `export async function generateMetadata()` — **動的**。リクエストごとに実行され、DB を引いて値を作れる。`app/reports/[id]/page.tsx` がこれで投稿タイトルを `<title>` に入れている。**サーバーコンポーネント限定**。
- 副作用の注意: `generateMetadata` とページ本体が**同じデータを別々に取りに行く**構造になるため、素朴に書くと同一リクエスト内で同じ DB クエリが2回走る。`reports/[id]/page.tsx` では React の `cache()` で `findReportById` を包み、リクエスト内で1回に重複排除している（`getReport`）。

### layout と page のマージ規則（ページが勝つ・フィールド単位）

layout と page の両方に定義がある場合、**フィールド単位の浅いマージでページ側が勝つ**。

- `/reports/[id]`: `title` はページの `generateMetadata` が上書き、`robots: noindex` はページが何も言っていないので layout の値が残る。
- `/users/[id]`: ページ側の宣言が無い → layout のデフォルトが素通し。**タブが常に「Errata Hub」になる正体はこれ**（SEO 着手時に `generateMetadata` を追加予定）。

### 確認方法

ブラウザで任意のページを開き、開発者ツールの Elements タブで `<head>` を見る。生成された `<title>` と `<meta name="robots" content="noindex, nofollow">` が確認できる（`<title>` はページの見た目には出ないので devtools かタブ表示でしか気づけない）。
